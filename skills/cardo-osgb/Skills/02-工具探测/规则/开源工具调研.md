# 开源算法 / 第三方工具 / 外部依赖调研（2026-10）

> 目的：回答「当前解析能力哪里弱、有没有更合适的开源工具、要不要换」。
> 结论先行：**主转换器不换**（`fanvanzh/3dtiles v0.4` 仍是开源 OSGB→3D Tiles 的事实标准）；
> 真正的短板不在"转不出来"，而在**转出来之后只用了 max-z 一个量**。本次改造因此落在
> 标准容器层（b3dm/GLB）的解析深度与几何算法上：法线顶面过滤、栋数闭运算、纹理分辨率/退化面/扩展名解析。
> 本文件同时是工具选型与后续集成的依据，**不含任何未落地的承诺**。

## 0. 我们当前实际拿到了什么（实测，非推测）

对本模型 44 个 b3dm 逐文件解析（`05` 的 `tiles_inspect.scan_products`）：

| 维度 | 实测 | 说明 |
|---|---|---|
| 图元 / 顶点 / 三角面 | 176 / 689,435 / 589,802 | 每 b3dm 4 个 primitive |
| NORMAL / TEXCOORD_0 / indices | 176 / 176 / 176 | **全都有** → 顶面过滤与纹理采样在数据上可行 |
| glTF 扩展 | `KHR_techniques_webgl`（44/44） | legacy 扩展；Cesium 可读，现代查看器兼容性差 |
| 纹理格式 | JPEG 176 张，128×128 – 1024×1024 | 无 KTX2/BasisU；无外链纹理 |
| b3dm featureTable | `BATCH_LENGTH` 44/44，`RTC_CENTER` 0/44 | 不依赖 RTC，几何在局部坐标 |
| 瓦片 x/y 重叠（IoU≥0.5） | 40 对 | LOD 是**空间分区 + 重叠**，取 max z 必然混粗/精模 |

这组事实决定了本轮改造方向：**有法线 → 可做顶面口径；有重叠 → 栋数需要去噪；有 JPEG → 可做纹理分辨率与
（下一阶段的）颜色语义**。

## 2. 三条短板的处理决定

### 2.1 转换路径单一

- 现状：只有 `fanvanzh/3dtiles v0.4`；它有 LOD 空间分区、纹理打包、ECEF 定位，且已加入白名单（sha256 + 178 文件指纹）。
- 决定：**不换**。理由：① 另一个开源可选项（OSG `osgconv`）只到 OBJ/glTF，仍需二次 tiling；
  ② 商业 SaaS 违反数据边界；③ 换转换器会让 527.427 m 配准缺陷、纹理打包方式、LOD 命名全部重验，收益不抵风险。
- 可做：把 OSG 作为**离线对照**（不进主链），只用于抽查几何量；需要时单独立项并登记工具。

### 2.2 几何分析只用了 max-z

- 现状：`v1` 把全部顶点投格取 max z，立面顶点抬高高度、碎片抬高栋数。
- 决定（已实施，`indicators-v1.1`）：
  1. **顶面优先**：读 `NORMAL`，只把 `NORMAL.z ≥ 0.5` 的顶点放进 `top` 网格；`auto` 模式在
     「法线顶点占比 ≥30% 且 ≥90% 观测格有顶面顶点」时启用（本模型 57.8% / 99.94% → 启用）。
  2. **栋数闭运算**：mask 先做 4 邻域 ×1 格闭运算再数连通分量（只在观测格内），本模型 27 → 18 个分量。
  3. **敏感区间不变**：仍是 0.5/1/2 m × 地面口径 × 层高 2.8/3.3 的 min–max。
- 未做（明确记录）：按三角面几何法线（重心法）分类、LOD 单层过滤、建筑实例分割。原因分别是：
  需要索引+顶点联合计算（成本高、收益待测）、单层 LOD 会丢覆盖（L20 只占 8/44）、实例分割需要标注/模型。

### 2.3 纹理/材质只计数不分类

- 现状：`greenery_ratio`、`road_ratio` 永久 `null`（`placeholder` + gap）。
- **已做 PoC（Pillow 11.3.0）**：解码 176 张内嵌 JPEG 的 64×64 缩略图，统计绿/灰/其它颜色占比：
  绿 P50 **7.0%**（按纹理字节加权 **11.4%**）、灰 P50 **56.4%**（加权 55.9%），色相峰值在 60–90°（46.9%）。
  结果写入 `过程文件/05-模型体检/纹理颜色诊断.json`（`cardo/lowair-texture/v1`，含 176 条逐图明细）。
- **进阶 PoC（Pillow + numpy + trimesh + scikit-image）**：按**朝上三角面重心**的 UV 采样纹理，投到 1.0 m 网格；
  绿色斑块先用 `skimage.morphology.closing`（disk 1）+ 连通域 ≥8 px 去噪：
  8,958 格 / 353,385 个面样本，绿 **17.0%**、灰 **60.1%**、其它 22.9%，4,813 个绿斑块，格内绿 P90 43.8%。
  明细写 `过程文件/05-模型体检/纹理按格颜色诊断.json`。
- 结论：**纹理确实携带植被/铺装信号**，且"按格"后可以给出空间分布；但它是「纹理覆盖面积」代理，
  仍不是平面用地面积（缺超像素/语义分割与标注真值）。因此 7 条指标保持 `null`。
- 下一步（明确条件）：① 用 scikit-image 超像素/聚类把屋面和植被分开；② 用 OpenCV 轮廓平滑；
  ③ 有 ≥1 片区人工标注后做混淆矩阵，通过才写入 `greenery_ratio` / `road_ratio`。
  在这三步完成前，不写任何绿化率/道路占比数字。

## 4. 集成路线（按优先级，均为增量、不破坏现有链）

1. **已做**：05 质量块 / LOD 统计 / Pillow 纹理颜色诊断；06 顶面 + 闭运算 + numpy 向量化；08 口径对账。
2. 下一阶段（需另立任务）：
   - **纹理语义按格统计**：UV + 三角面反投影到 06 网格，再叠 scikit-image 超像素/聚类；有标注后做混淆矩阵，
     通过了才写入 `greenery_ratio` / `road_ratio`。
   - **trimesh 面法线**：按三角面重心法线分类顶面，替代顶点法线阈值，评估漏计率。
   - **gltf-transform / gltfpack**：作为可选压缩/简化器（先登记版本/许可/sha256，再改 03 的 `--optimize` 开关）。
3. 不做：自研 OSGB 解析器；把 b3dm/tileset 当交付；未登记二进制进 `tools/`。
