# 算法说明（人读版）

> 机器读的那份是 [`算法注册表.json`](算法注册表.json)（同一份表，CLI 直接读它）；本文件讲**怎么用、状态怎么理解、怎么加算法**，不重复抄表。

## 为什么会有这份表

原来的链路把算法写死在脚本里：能跑什么、为什么跑，只有读代码才知道。结果就是——
`调研无人机算法平台功能汇总表.xlsx` 里列了 21 个开源项目，**在 CardoOSGB 里一个都没用上**，
不是它们不好，而是链路里没有「算法是什么、要什么输入、产出什么」这一层。

现在把每个算法登记成一条记录（53 条），每条都写清四件事：

| 字段 | 回答的问题 |
|---|---|
| `plain` | **这个算法是干什么的**（人话，不写公式） |
| `input` | 要什么输入（模型？影像？两期？真值？） |
| `output` | 产出什么（哪个文件、哪个键） |
| `status` / `reason` | 现在能不能跑；不能跑**卡在哪** |

## 四种状态

| status | 意思 | 处理方式 |
|---|---|---|
| `ready` | 现在就能跑，输入本链已有 | 选它就会真的执行 |
| `needs-imagery` | 算法本身可用，但需要**原始航摄影像**（本链只有模型，没有原片） | 不执行，`--skip-unavailable` 时跳过并说明原因 |
| `needs-2epoch` | 需要**两期**数据才能做变化检测 | 同上 |
| `needs-truth` | 需要**标注真值**才能给出精度（不是算不出来，是不能声称精度） | 同上 |
| `planned` | 还没实现 | 只登记，不执行 |

**关键**：`needs-*` 不是「做不到」，而是「差一样东西」。这条差别写进 `reason`，用户看到的是
「要什么才能跑」，不是一句「不支持」。

## 三种用法

### 1. 看有什么（`algos`）

```bash
python Skills/00-Cardo低空解析总控/scripts/pipeline.py algos
python Skills/00-Cardo低空解析总控/scripts/pipeline.py algos --group recon
python Skills/00-Cardo低空解析总控/scripts/pipeline.py algos --status ready
```

输出分两段：前半是「每个算法的编号 / 名称 / 状态 / 适用步骤」，后半是「人话说明 + 要什么 + 产出什么 + 不可用原因」。
编号（`#1`…`#53`）只是展示用，**选的时候用 id**（如 `recon.ndsm`）或编号都行。

### 2. 交互选（`run --select`）

```bash
python Skills/00-Cardo低空解析总控/scripts/pipeline.py run --select
```

会把全部算法按组列出来，等你输入编号（逗号/空格分隔，`all` 全选，空回车取消）。
选完自动换算成「要跑哪几步」；如果某个前置步骤的产物还没生成，会**从最早缺料那步补跑**，不会让你先手动跑一遍。

先看计划不执行：

```bash
python Skills/00-Cardo低空解析总控/scripts/pipeline.py run --select --dry-run
```

### 3. 直接点名（`run --algos`）

```bash
python Skills/00-Cardo低空解析总控/scripts/pipeline.py run --algos recon.ndsm,recon.instance,vector.topology
python Skills/00-Cardo低空解析总控/scripts/pipeline.py run --algos recon.ndsm,imagery.3dgs --skip-unavailable
```

`--skip-unavailable`：点到 `needs-*` 的算法时不报错，跳过并在运行报告里写原因。

## 分组

| group | 含义 | 典型算法 |
|---|---|---|
| `ingest` | 输入接入与解包 | 路径安全、zip 校验、EPSG 合规 |
| `check` | 模型体检 | b3dm 容器读取、纹理分辨率、退化三角面、契约自检 |
| `metric` | 2.5D 现状指标 | 每格最高点 DSM、局部 P10 地面、顶面口径、闭运算栋数、容积率 |
| `recon` | 三维要素反演（09） | 顶面 DSM、地面参考面、nDSM、阈值+形态学、分水岭实例化、OBB、置信分级 |
| `vector` | 矢量入库（10） | 拓扑清理、属性表、字段字典 |
| `store` | 成果导出 | xlsx/docx 回读校验 |
| `enhance` | 几何增强（11/12/13） | 地面滤波、栅格分类、单木分割、网格修复、屋面分割、立面法向、轮廓矢量化、GeoPackage 入库 |
| `imagery` | 需要原片（本链缺） | 空三、点云加密、纹理重建、3DGS/NeRF 等 |
| `twoepoch` | 需要两期 | 变化检测、建筑拆除/新增 |
| `planned` | 未实现 | 语义分割、单体化 LOD、规则化建模 |

## 怎么加一个算法

1. 在 `算法注册表.json` 的 `algos[]` 里加一条，**必须填** `id/name/group/step/status/default/plain/input/output/source`；
2. 能跑的（`ready`）→ 实现脚本、把 `step` 指到对应技能目录，并在 `pipeline.py` 的 `STEPS` 里有这一步；
3. 不能跑的（`needs-*`）→ `reason` 写清「缺什么、补上就能跑」，不要写「不支持」；
4. 改了表就跑一次 `algos` + `run --algos <新id> --dry-run`，确认能解析、能换算出正确步骤。

### 随包自带的那份（不用跑就有）

交付包里**已经放好一份**现成的表，拷到任何机器直接双击就能看，不必先跑流水线：

| 文件 | 位置 | 是什么 |
|---|---|---|
| `算法清单与来源.xlsx` | `assets/算法表/` | 上面那四张表（随包快照，与注册表同源） |
| `调研算法表_开源21项.xlsx` | `assets/算法表/` | **原始调研表的「开源」sheet**（21 个项目的要素类别/链接/适配度/验证结果）——这是上面第一张表的对照底稿 |
| `调研成果/uav-imagery-algo-research.html` | 包内：`参考依据/算法表调研成果/`（相对包根；随包分发） | 调研报告全文（双击打开，离线可看）：表内 21 项为什么没用上、表外还能找什么 |

三份文件构成完整链路：**用了什么算法**（前两表）→ **为什么这么选**（报告）。

注册表改了要同步随包那份：

```bash
python Skills/00-Cardo低空解析总控/scripts/export_algo_table.py --workspace . --package
```

`--package` 覆盖 `assets/算法表/算法清单与来源.xlsx`；不加 `--package` 则输出到工作区根（不碰包）。

事实口径（2026-10-29）：**表内 21 项采用 0 项**——它们全部依赖原始航摄影像或近景/红外影像，
本工作区只有重建后的 OSGB；能跑的 34 条全部来自「本链自研几何方法 + 通用开源库（numpy/scipy/scikit-image/
trimesh/Pillow/openpyxl/python-docx）+ 3dtile.exe」。这不是取舍，是数据条件决定的。

每条算法的 `sourceName`（具体项目/论文/规范）、`sourceLink`、`license`、`impl`（自实现/调库/外部工具）、
`evidence`（落在哪个文件哪段）都写在注册表里，表从注册表生成，改注册表再跑一次即同步。

## 和调研报告的关系

调研报告回答「表里 21 个项目为什么没用上、表外还能找什么」；本注册表回答「所以现在能用哪些、还差什么」。
两者用同一个 `source` 字段对齐：注册表里每条 `source` 都能在报告里找到对应条目。
