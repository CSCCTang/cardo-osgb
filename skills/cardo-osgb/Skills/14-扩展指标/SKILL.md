# 14 · 扩展指标汇总

## 为什么有这一步

第 06 步产出的是**规划口径的核心 7 条指标**（建筑密度 / 栋数 / 高度 P50、P90 / 容积率估算 /
绿化率 / 道路占比），其中后两条在本链的数据条件下只能占位。

但本链在 09–13 步已经落地了 20 多条算法——点云分类、单木分割、屋面分割、立面统计、
轮廓矢量化、GeoPackage 入库等——**这些算法的产出原先只躺在过程文件里，没进任何成果**。
交付出去时，对方只看到 7 条指标（还是 5 条有数），完全看不出用了什么算法、算出了什么。

本步解决这个断层：**把上游已算出的量汇成一张可回溯的扩展指标表**。

## 纪律

| 约束 | 落地方式 |
|---|---|
| **不新算几何** | 只从各步 summary 取已算好的字段，不引入第二套实现，不重算 |
| **不编数** | 上游没跑 / 没有该字段 → `value=null` + `grade=placeholder` + gap 条目 |
| **不硬凑区间** | 只有上游自己做过敏感性分析的指标才带区间，其余给单点值 + 置信度 |
| **必须可回溯** | 每条带 `algoId`（注册表里的算法 id）/ `step`（产自哪一步）/ `evidence`（哪个文件的哪个字段） |

## 输入 / 输出

| 项 | 路径 |
|---|---|
| 输入 | `过程文件/09-三维要素反演/三维要素反演.json`、`10-矢量入库/拓扑清理.json`、`11-几何增强/*/*.json`、`12-屋顶与立面/*/*.json`、`13-矢量增强/*/*.json` |
| 输出 | `过程文件/14-扩展指标/扩展指标.json`、`扩展指标.md` |

## 跑法

```bash
python Skills/14-扩展指标/scripts/build_extended_metrics.py --workspace .
```

由总控自动调用（`--to 14`）。跑完后总控会**自动重跑 07 与 08**——扩展指标要并进
《现状指标.xlsx》的「扩展指标」「算法溯源」两张 sheet 和《指标说明.docx》的第 5 节，
成果变了，边界扫描与基线对账也得跟着重核一次。

## 附：第 15 步「可观测类型矩阵」

14 步给出「算出了什么」，15 步给出「**这套技术到底能扫到什么**」——产品边界视角。

| 列 | 内容 |
|---|---|
| 类型 | 17 类可观测信息（建筑本体 5 / 地表场地 5 / 隐患状态 4 / 闲置效能 1 / 附属其它 2） |
| 扫描得到什么 | 人话描述这一类扫出来是什么 |
| 靠什么原理 | 用什么数据/算法能提取 |
| **开源算法供给** | 抄自调研表 21 项的要素类别归属（PolyR-CNN 5 项、DBA-RTMDet 5 项等） |
| 本链状态 | 已落地 6 / 部分落地 6 / 未做 5 |
| 本链链出的量 | 该类在本链的实际产出与实测值 |

**「开源算法供给」不是自拟的**——直接抄  的要素类别列。
分类基准是课题任务书 §2.1.1 的「核心数据」清单。

## 读表时必须一起看

1. **扩展指标 ≠ 新精度**：是上游算法已算结果的搬运，上游各自的局限同样适用。
2. **口径不同不可混比**：扩展表的栋数（几何实例化，13 栋）与 06 的栋数（2.5D 网格连通块，18 栋）
   是两个算法、两个口径，数值不同是正常的，不是矛盾。
3. **植被占比 ≠ 绿化率**：几何植被只覆盖可见树冠；规划口径的绿化率仍需影像语义分割。
4. **面积比 < 1 说明是异形建筑**：轮廓面积/外接矩形面积明显小于 1，说明这些楼是 L 形或异形，
   不能按矩形入库。

## 退出码

0 通过 / 2 输入缺失 / 3 闸门未过（指标结构不对）。
